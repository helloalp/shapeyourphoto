# 废片与清理候选决策机制

本文记录系统生成“不适合保留图片”建议，并执行安全清理逻辑的防护边界。

> [!NOTE]

## 定位与约束属性

系统的 `Cleanup Candidate` 逻辑是一个辅助判定标记，表示“该图片极大概率无保留价值”。
- 它不是一个强制指令，系统绝对不会因为该标记而自动静默执行删除。
- 它的引入初衷是减少明显无价值照片消耗系统的修复算力，并协助用户管理空间。

## 拦截与用户控制机制

- **分离式展示**：带有建议清理标记的图像被独立归集，并支持用户主导下的多选撤销或强制保留。
- **与修复流程的阻断**：为了防止徒劳的算力浪费，被打上清理建议标记的图片默认不可进入修复链路；必须通过用户端主动勾选“强制修复”才能突破拦截。
- **强制尝试的底线防御**：即便强行启动针对此类图片的修复，如果底层评估其增强效果微弱，其仍会受到 No-op 规则拦截，系统会拒绝保存劣化结果并终止流程。

## 安全退役路线

当用户最终采纳清理建议时，针对这批图片的实际移除将被强制路由至应用统一配置的安全删除沙箱流（`safe_cleanup_paths`）：
1. 系统先向底层文件系统发出版图剥离请求并投递到系统级安全回收站。
2. 如系统回收站环境不可用，则启动备用隔离预案，将其搬运至该软件工程目录下的隔离抽屉文件夹中暂存，以防追溯丢失。
3. 应用代码的任何地方都不得存在绕开这些防御手段而直接硬触发底层销毁的 `unlink` 行动。
